BUILD NOTES · OCTOBER 20, 2026

A correction must survive the next session.

A support assistant remembers that a successful transaction with a missing balance should go to the wallet team. Later, a reviewer withdraws that shortcut: transaction success does not prove that the intended recipient received the intended asset or amount. The important test comes tomorrow. Does the assistant still apply the old instruction?

RecallDesk explores that narrow problem. It keeps an append-only history of curated support lessons, corrections and revocations in Walrus Memory. Tatum checks the transaction supplied with a ticket. The policy layer then explains what evidence applies, or asks for human review.

The mistake in our first evaluation

The first version compared six synthetic tickets with an empty rule set and called matching all six a gain. That was too weak. A fixed knowledge base could match those cases too. We replaced that claim with nine explicit memory-lifecycle cases and four comparisons. These cases were written alongside the implementation; they are contract checks, not an independent accuracy benchmark.

Complete replay ties a correctly maintained database. Its purpose here is portable review history and inspectable receipts, not a claim that decentralized storage improves reasoning. The six reviews are expected in these constructed cases. Real tickets could expose excessive abstention; that remains unmeasured.

Retrieval is not a complete ledger

Semantic recall can return an old matching lesson and omit its correction or revocation. Sorting the retrieved candidates by date cannot recover a missing candidate. RecallDesk records every accepted job and completed blob, then requires all expected records before applying revisions. Missing a record makes the read fail. Duplicate IDs with different content and conflicting revisions also fail.

This is intentionally bounded: one writer, at most 50 records, and completeness relative to that writer's receipt manifest. Unknown writes from another client are not guaranteed to be detected. Walrus Memory's stable SDK and newer documentation expose different enumeration capabilities; this prototype uses the stable SDK's recall response and checks it against receipts.

What actually ran

We wrote twelve synthetic lesson/review records to Walrus Mainnet, then a thirteenth record revoking the API-authentication lesson. A new process recovered all thirteen and routed the API ticket to human review. Separately, Tatum returned a real Sui Mainnet transaction and its effects. The combined run recovered the corrected memory and required recipient, asset and amount checks instead of inferring a display fault.

The demo's live-evidence button performs those provider reads on the server. It exposes no keys and accepts no public memory writes. A successful result may be reused for sixty seconds and shows its check time. Provider failures produce an unavailable result; they do not silently substitute sample data.

What this prototype does not establish

The support tickets and review history are synthetic. Routing is a deterministic policy matcher, not an LLM. Negation triggers conservative review, which can over-abstain. A real transaction attached to a synthetic complaint proves the integration path, not that an actual customer's complaint was resolved. Tatum's JSON-RPC read worked during verification, but its announced deprecation makes gRPC migration a production requirement.

The next useful evidence would be independently reviewed incidents and a replay against a properly maintained support knowledge base. More sample tickets alone would not establish that claim.
